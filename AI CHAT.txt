> padStart напомни что это ?

● padStart — метод строки. Он дополняет строку слева указанным символом, пока
  она не станет нужной длины.

  str.padStart(targetLength, padString)

  - targetLength — какой длины должна стать строка.
  - padString — чем дополнять слева (по умолчанию пробел).

  Если строка уже не короче targetLength, она возвращается без изменений.

  '9'.padStart(2, '0')   // '09'
  '15'.padStart(2, '0')  // '15'
  '5'.padStart(4, '0')   // '0005'

  В minutesToTime он нужен, чтобы часы и минуты всегда были двузначными:

  minutesToTime(545)  // 9 ч 5 мин
  // без padStart: '9:5'
  // с padStart:   '09:05'

  Без этого результат не прошёл бы проверку TIME_REGEX и не совпал бы с форматом
  HH:mm из контракта. Есть и парный метод padEnd: он дополняет строку справа.

● Что такое MSW

  MSW (Mock Service Worker) перехватывает HTTP-запросы прямо в браузере. При
  запуске приложения регистрируется Service Worker (тот самый
  public/mockServiceWorker.js). Когда axios отправляет GET
  /api/bookings?date=..., воркер ловит запрос и отдаёт его твоему обработчику
  (handler), а обработчик возвращает ответ, как настоящий сервер.

  UI → axios → GET /api/bookings → [Service Worker] → handler в src/mocks →
  JSON-ответ

  Для UI и axios это обычный сервер: в DevTools во вкладке Network видны
  настоящие запросы и ответы. Поэтому сетевой слой пишется под реальный API, и
  потом достаточно просто не запускать MSW.

  Внутри src/mocks обычно три части:
  - db — хранилище в памяти: массив броней со стартовыми данными, функции
    добавить, изменить, удалить.
  - handlers — http.get / post / patch / delete('/api/bookings...'), каждый
    возвращает HttpResponse.json(...) с нужным статусом.
  - browser.ts — setupWorker(...handlers); в main.tsx перед рендером вызывается
    worker.start().

  Да, проверка нужна и на сервере

  По ТЗ сервер сам проверяет бизнес-правила и умеет отвечать 409. Проверка нужна
  в двух местах, и у каждого своя задача:

  ┌───────────┬──────────────────────────────┬─────────────────────────────┐

  │           │ удобство: сразу показать     │ источник истины: клиенту    │
  │ Зачем     │ ошибку, заблокировать        │ нельзя доверять, данные     │
  │           │ занятые варианты             │ могли устареть              │
  ├───────────┼──────────────────────────────┼─────────────────────────────┤

  │           │ ошибка у поля, кнопка        │ 422 — нарушено правило, 409 │

● Потому что в этом задании сервер — это и есть твой MSW. Настоящего бэкенда

  Проверка только на клиенте не спасает по трём причинам:

  1. Устаревшие данные. Клиент проверяет по списку броней, загруженному какое-то
     время назад. Пример:
     - в 10:00 ты открыл форму, слот 12:00–13:00 свободен;
     - в 10:01 коллега забронировал 12:00–13:00;
     - в 10:02 ты нажимаешь «Create» — клиентская проверка проходит, данные-то
       старые.

     Поймать это может только сервер: у него актуальный список. Это ровно
     правило 8 из ТЗ.
  2. Клиент можно обойти. Запрос можно отправить через curl, Postman или
     поправить в DevTools. Сервер не должен доверять тому, что пришло с клиента.
  3. Это требование ТЗ. «Сервер валидирует бизнес-правила и умеет возвращать
     конфликт (409)». И отдельно оценивается обработка серверных ошибок. Если
     сервер ничего не проверяет, 409 взяться неоткуда, и показать его обработку
     не получится.

  - клиент нужен для удобства: ошибка видна сразу, занятые варианты недоступны,

  2. handlers.ts — «роуты»

  По одному обработчику на каждый запрос из контракта. По сути это мини-Express:

      if (!date) return HttpResponse.json({ message: 'date is required' }, {

      await delay(500)
      const input = (await request.json()) as BookingInput
      const error = validateBooking(input, { bookings: db.getAll(), now: dayjs()
  })
      if (error) {
        const status = error.code === 'OVERLAP' ? 409 : 422
        return HttpResponse.json(error, { status })
      }
      return HttpResponse.json(db.create(input), { status: 201 })
    }),

    http.delete('/api/bookings/:id', ...),
  ]

  Где лежат моки по FSD

  В FSD нет отдельного слоя для моков. Это нормально, потому что моки — не часть
  приложения, а его окружение, как тесты или конфиги. Поэтому src/mocks лежит
  рядом со слоями, а не внутри них:

  src/
    app/ pages/ widgets/ features/ entities/ shared/   ← приложение (FSD)
    mocks/                                             ← инфраструктура, вне
  слоёв
    main.tsx

  Почему не внутри слоёв:
  - shared не подходит. Моки используют validateBooking и типы из
    entities/booking. А по правилам FSD shared — нижний слой и не может
    импортировать из entities.
  - app нарушил бы разделение. Технически app может импортировать что угодно, но
    тогда моки станут частью приложения. Мы же хотим, чтобы их можно было
    отключить или удалить без последствий.
  - Импортирует их только main.tsx, и только динамически по флагу. Ни один слой
    приложения не знает о моках. Поэтому при переходе на реальный API достаточно
    выставить VITE_API_MOCKING=false или удалить папку.

> isSame напомни что? понятнее как будет

● isSame — метод dayjs, который сравнивает две даты с точностью до указанной
  единицы:

  value.isSame(dayjs(), 'day')

  Читается так: «value — тот же день, что и сейчас?» Второй аргумент задаёт
  точность сравнения:
  - 'day' — совпадают год, месяц и день, время не учитывается;
  - без аргумента — сравнение до миллисекунды, и с dayjs() почти никогда не
    совпадёт.

  dayjs('2026-10-28 09:00').isSame(dayjs('2026-10-28 17:45'), 'day')  // true
  dayjs('2026-10-28').isSame(dayjs('2026-10-29'), 'day')              // false
  dayjs('2026-10-28').isSame(dayjs('2026-11-28'), 'month')            // false

  Похожие методы: isBefore(x, 'day') и isAfter(x, 'day'). Мы их уже используем в
  validateBooking для проверки прошедших дат.

  Как сделать понятнее

  У dayjs есть плагин isToday, он делает ровно эту проверку:

  import isToday from 'dayjs/plugin/isToday'
  dayjs.extend(isToday)

  value.isToday()

  Читается лучше, но плагин нужно подключить один раз при старте приложения,
  например в app/ или в shared/lib. Иначе TS и рантайм не будут знать про метод.

  Я бы оставил isSame(dayjs(), 'day'): это стандартный API без подключений, и та
  же форма записи уже есть в validateBooking. Понятность здесь даёт имя
  переменной isToday. Если хочешь value.isToday(), подключу плагин.

  if (error) return validationErrorResponse(error)
  if (isSimulatedConflict()) return simulatedConflictResponse()

  Как это работает:
  - Счётчик идёт только по запросам, прошедшим валидацию. Если запрос не прошёл
    валидацию, он вернёт свою ошибку 422 или настоящую 409 и счётчик не
    увеличит. Поэтому «через раз» считается по валидным запросам.
  - Счётчик общий для POST и PATCH. Создал бронь — успех, следующее
    редактирование — 409, следующий запрос снова пройдёт.
  - База не меняется. После 409 список перезапросится, но в нём ничего не
    изменится, и повторная отправка тех же данных пройдёт. Это ровно сценарий из
    ТЗ: сервер вернул конфликт, хотя UI считал слот свободным.
  - Для проверки правила 8: создай бронь — она сохранится. Создай вторую —
    увидишь алерт, введённые данные останутся, в Network появится повторный GET.
    Нажми «Create» ещё раз — бронь сохранится.

  Что учесть:
  - Это поведение и на задеплоенном демо. Половина сохранений будет падать — это
    стоит указать в README, иначе проверяющий примет это за баг.
  - После перезагрузки страницы счётчик сбрасывается вместе с базой.
